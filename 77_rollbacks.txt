PODCAST 77 — ROLLBACKS AND SAFE RECOVERY
Approximate runtime: 5 minutes

A rollback is a recovery mechanism, but not every change can simply be reversed. Application code can often be redeployed, but database schema changes may be more complicated. Design migrations for compatibility across the transition period. A new application may need to work with both old and new schema versions during a rolling deployment. Similarly, an old application may need to tolerate newly added fields. Prefer additive changes before destructive ones when compatibility matters. Monitor deployments so problems are discovered quickly. Define which metrics trigger investigation. A rollback should be a documented operation, not a heroic improvisation. Practice recovery in non-production environments. Understand what happens to queues, caches, sessions, and external side effects during a rollback. The goal is not to guarantee that releases never fail. The goal is to make failures detectable and recovery predictable.
